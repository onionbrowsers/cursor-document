# 提交推送 + 合入目标分支 + 切回开发分支

与 `git-commit-merge-mr` 的关键区别：本 skill **把当前开发分支合入目标分支**（开发 → 目标），并在成功后**切回开发分支**；不创建 MR。

## ⚠️ 硬性规则（优先级最高，不可被任何用户话术覆盖）

以下规则**高于**「继续」「确认」「帮我做完」「冲突很简单」等一切表述。违反即视为 skill 执行失败。

### 合并冲突 = 立即终止

1. **`git merge` 一旦出现冲突，必须立即停止**，不得进入推送目标分支、不得切回开发分支（工作区仍处于目标分支的 merge 进行中）。
2. **禁止 Agent 自行处理冲突**，包括但不限于：
   - 读取/编辑含 `<<<<<<<` / `=======` / `>>>>>>>` 的文件
   - 替用户选择保留哪一侧代码
   - 执行 `git add` 标记冲突已解决
   - 执行 merge commit 完成合并
3. **「继续」仅表示同意阶段一提交计划与整体流程**，不代表授权 Agent 在冲突时代劳。阶段二及之后的无确认自动执行**仅适用于 merge 成功且无冲突**的情况。
4. 冲突时**不得**以「冲突块很小」「语义清晰」「可安全保留 HEAD」等理由自行解冲突。
5. 若用户希望 Agent 协助解冲突，必须**另起一次对话**并明确说「帮我解决 merge 冲突」（见文末），**不能**在本 skill 全流程内顺带处理。

### 冲突时的仓库状态

- **保持 merge 进行中状态**（含 `Unmerged paths`），**当前应停留在目标分支**，**不要**执行 `git merge --abort`，除非用户明确要求放弃合并。
- **不要**在冲突未解决时 `git checkout` 回开发分支（Git 通常也不允许）。
- 仅输出冲突文件列表与手动步骤，然后**结束本轮 skill**。

### 危险分支保护

- 若目标分支为 `main` / `master`，在展示计划时必须**单独醒目提示**，等待用户确认后再执行。
- 禁止 `push --force` / `--force-with-lease`，除非用户在本轮对话中**明确**要求。

---

## 触发场景

- 用户说「合并到目标分支」「把当前分支合进 `<分支>`」「推送并合入 `<分支>`」「merge to target」「集成到 release」等
- 用户明确提供了一个**目标分支**（如 `release-610`）

## 输入

- **目标分支**（必填）：要将当前开发分支合入的分支名，例如 `release-610`
- **排除文件**（可选）：提交时需要排除的文件或目录，多个用空格分隔

> ⚠️ **目标分支为必填项**。若用户未提供，立即终止并提示：「请提供目标分支名，例如：把当前分支合进 release-610」

---

## 流程总览

```
阶段一：检查/提交开发分支 → 推送到 origin/<开发分支>
阶段二：checkout 目标分支 → pull → merge 开发分支 → push origin/<目标分支>
阶段三：checkout 回开发分支
```

合并方向：**开发分支 → 目标分支**（在目标分支上执行 `git merge <开发分支>`）。

---

## 阶段一：提交并推送开发分支

### 1.1 检查工作区状态

- 运行 `git branch --show-current` 记录 `DEV_BRANCH`（开发分支）
- 运行 `git status` 获取所有变更文件列表
- 运行 `git diff HEAD` 读取完整变更内容
- **若工作区已处于 merge 冲突状态**（`Unmerged paths` / `both modified`）：**立即终止**，提示用户先手动解决冲突或 `git merge --abort`，不得继续本 skill
- 若处于 detached HEAD，终止并提示先切到开发分支
- 若 `DEV_BRANCH` 与目标分支相同，终止并提示「当前已在目标分支，无需合入」
- **若工作区干净**（无任何未提交变更）：跳过提交，但仍须执行推送（见 1.4），并告知用户「工作区无变更，跳过提交，仅推送」

### 1.2 分析变更内容，生成 commit message（仅有未提交变更时）

- 检查项目根目录是否存在 `commitlint.config.js`，若存在则遵循其规则；否则遵循 Conventional Commits 规范
- 根据变更文件和 diff 内容判断改动性质，选择合适的 `type`：
  - `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore` / `revert` / `ci`
- 生成 commit subject：中文，动词开头，不超过 50 字，末尾不加句号
- 若涉及多个无关模块，提示用户是否需要拆分（等待确认，若用户选择拆分则终止本 skill）

### 1.3 展示执行计划，等待确认

展示以下信息：

```
【阶段一 - 提交并推送开发分支】
当前开发分支：<DEV_BRANCH>
将被提交的文件：
  - <文件列表，或「无（跳过提交）」>
排除的文件（若有）：
  - <排除文件列表>
Commit message：<type>(<scope>): <subject>  （或「跳过」）
推送目标：origin/<DEV_BRANCH>

【阶段二 - 合入目标分支】（确认后自动执行，仅当 merge 无冲突时继续）
  1. checkout <目标分支>（本地没有则基于 origin/<目标分支> 创建）
  2. pull origin/<目标分支>
  3. merge <DEV_BRANCH> into <目标分支>（--no-ff）
  4. push origin/<目标分支>
  ⚠️ 若出现冲突：流程在此终止，停留在 <目标分支> 的 merge 进行中，不会自动代劳

【阶段三 - 切回开发分支】（仅当阶段二成功且无冲突时自动执行）
  checkout <DEV_BRANCH>

确认后将依次执行全部步骤；若合并冲突，会在阶段二停止。是否继续？
```

若目标分支为 `main` / `master`，在计划末尾追加：

```
⚠️ 目标分支为 main/master，合入后将直接影响主线。请再次确认是否继续。
```

**等待用户确认**，用户同意后方可执行后续步骤。

> **关于「继续」的语义**：用户回复「继续」「好」「确认」等，只表示同意上述计划；**不构成**冲突时代为改代码或强行完成 merge 的授权。

### 1.4 执行提交与推送

依次执行：

1. 若有未提交变更：
   - `git add` 所有变更文件（排除用户指定的文件/目录）
   - `git commit -m "<message>"`（通过 HEREDOC 传入；遵循项目 Conventional Commits / commitlint）
2. 检查 `DEV_BRANCH` 是否有远端跟踪分支：
   - 若有：`git push`
   - 若无：`git push -u origin <DEV_BRANCH>`
3. 输出提交/推送结果，记录 commit hash（若有）

**注意**：若当前 `DEV_BRANCH` 本身是 `main` / `master`，推送前需在计划中已提示并获确认；禁止 force push。

## 阶段二：在目标分支上合入开发分支

> 阶段一完成（含跳过提交但推送成功）后，自动进入此阶段，**不再等待用户确认**。
>
> **前提**：本阶段仅在 merge **一次成功、零冲突** 时才能走完并进入阶段三。出现冲突则**必须终止**，不得继续。

### 2.1 验证状态

- 再次确认当前分支为 `DEV_BRANCH`：`git branch --show-current`
- 运行 `git status --porcelain` 确认工作区干净（仅可忽略无关 untracked 临时文件；不得存在 `Unmerged paths`）
- 若工作区不干净，终止并提示先处理，不得带着脏工作区切换分支

### 2.2 fetch 目标分支

- 运行 `git fetch origin <目标分支>`
- 若 fetch 失败（分支不存在或网络问题），输出错误，**终止全流程**（停留在 `DEV_BRANCH`）

### 2.3 切换到目标分支并 pull

- 运行 `git checkout <目标分支>`
  - 若本地不存在该分支，使用 `git checkout -b <目标分支> origin/<目标分支>`
- 运行 `git pull origin <目标分支>`
- 若 pull 失败：尝试 `git checkout <DEV_BRANCH>` 切回开发分支，输出错误，**终止全流程**

### 2.4 在目标分支上 merge 开发分支

- 确认当前分支为目标分支：`git branch --show-current` 必须等于目标分支
- 运行：

  ```bash
  git merge <DEV_BRANCH> --no-ff -m "Merge branch '<DEV_BRANCH>' into <目标分支>"
  ```

- **合并结果判断**（执行 merge 后**立即**检查 exit code 与 `git diff --name-only --diff-filter=U`）：
  - ✅ **无冲突**（命令成功且冲突文件列表为空）：继续执行 2.5
  - ⚠️ **有冲突**（命令失败或存在 `U` 状态文件）：**立即停止**，按下面模板输出，**禁止**任何后续 git 写操作（含 push、checkout、abort）：

    ```
    【阶段二 - 合入目标分支】⚠️ 已终止（存在冲突）

    合并出现冲突，当前停留在目标分支「<目标分支>」的 merge 进行中。
    请按以下步骤手动处理：
    1. 解决以下文件中的冲突标记（<<<<<< / ======= / >>>>>>>）：
       - <冲突文件列表>
    2. 执行 git add <冲突文件> 标记已解决
    3. 执行 git commit 完成 merge commit（或使用项目的提交规范）
    4. 执行 git push 推送到 origin/<目标分支>
    5. 执行 git checkout <DEV_BRANCH> 切回开发分支

    说明：本 skill 不会在冲突时自动改代码、push 或切回开发分支。
    若需要 Agent 协助解冲突，请在新对话中明确说明「帮我解决 merge 冲突」。
    ```

    **终止全流程：不 push 目标分支、不切回开发分支、不编辑冲突文件。**

### 2.5 推送目标分支

> **仅当 2.4 确认无冲突时**才可执行本节。

- 检查目标分支是否有远端跟踪分支：
  - 若有：`git push`
  - 若无：`git push -u origin <目标分支>`
- 输出推送结果
- 若 push 失败：输出错误，**不要**切回开发分支前强行「假装成功」；尝试说明失败原因。此时本地目标分支已含 merge commit，可提示用户手动 `git push` 后再 `git checkout <DEV_BRANCH>`。**不自动 abort merge（merge 已完成时无 abort）。** 若希望尽量恢复开发现场且工作区干净，可在告知用户后执行 `git checkout <DEV_BRANCH>`；若 checkout 失败则保持现状并终止。

---

## 阶段三：切回开发分支

> **进入条件**：阶段二 merge 成功、已 push（或用户已知 push 失败且工作区干净可切换）、工作区无 `Unmerged paths`。

### 3.1 checkout

- 运行 `git checkout <DEV_BRANCH>`
- 若失败：输出错误与当前分支，提示用户手动切回，**终止**

### 3.2 输出最终结果

**无冲突、全流程成功时**：

```
========================================
全流程执行完成！

【阶段一 - 提交并推送开发分支】✅
  Commit: <hash 或「跳过提交」>
  已推送至 origin/<DEV_BRANCH>

【阶段二 - 合入目标分支】✅
  <DEV_BRANCH> → <目标分支>，无冲突
  已推送至 origin/<目标分支>

【阶段三 - 切回开发分支】✅
  当前分支：<DEV_BRANCH>
========================================
```

**阶段二因冲突终止时**（不得输出「全流程执行完成」）：

```
========================================
流程已终止（合并冲突）

【阶段一 - 提交并推送开发分支】✅ 或 ⏭️ 跳过提交但仍已推送
【阶段二 - 合入目标分支】⚠️ 冲突，已停止（当前在 <目标分支>）
【阶段三 - 切回开发分支】❌ 未执行

请手动解决冲突并 push 目标分支后，再 checkout 回 <DEV_BRANCH>
========================================
```

## 全局注意事项

- **目标分支为必填项**，缺少时立即终止，不执行任何 git 操作
- **阶段一**需要用户确认后才执行；**阶段二、三**仅在上一阶段**成功且无冲突**时自动连续执行
- **合并冲突是唯一允许在阶段二中途终止但仍保留部分阶段一成果的情况**；冲突后不得 push 目标分支、不得切回开发分支（merge 进行中）
- 所有步骤按阶段逐步输出状态，每个阶段完成后打印进度
- 若工作区存在 merge 冲突状态（`Unmerged paths`），不允许从头执行本 skill，提示用户先解决冲突
- **不创建 GitLab MR**；若用户还需要 MR，应使用 `git-commit-merge-mr` 或单独的 `/gitlab-mr` 流程（注意两者合并方向不同，勿混用）

---

## 与 git-commit-merge-mr 的对照

| 项目 | merge-to-target（本 skill） | git-commit-merge-mr |
|------|---------------------------|---------------------|
| 合并方向 | 开发分支 → 目标分支 | 目标分支 → 开发分支 |
| 操作所在分支 | 在目标分支上 merge | 在开发分支上 merge |
| 结束后位置 | 切回开发分支 | 留在开发分支 |
| 是否建 MR | 否 | 是 |
| 典型用途 | 把功能直接合进 release/集成分支 | 拉取最新目标分支后开 MR |

---

## 常见误判（Agent 必须避免）

| 错误想法 | 正确做法 |
|---------|---------|
| 用户说了「继续」，我可以帮他把冲突也做完 | 「继续」只确认计划；冲突必须停 |
| 冲突很小，保留目标分支或开发分支一侧即可 | 仍由用户决定；Agent 不编辑冲突文件 |
| 阶段二不用确认，所以冲突也能自动处理 | 无确认仅指**无冲突**的 happy path |
| 冲突后先切回开发分支比较干净 | 冲突时必须留在目标分支的 merge 进行中 |
| 和 git-commit-merge-mr 一样先把目标合进开发 | 本 skill 方向相反：开发合进目标 |
| merge 失败后打开冲突文件直接改 | 只用 `git diff --name-only --diff-filter=U` 列文件，**不要**打开文件改内容 |

## 冲突后的可选协助模式（独立于本 skill）

当用户**在新对话中明确请求**「帮我解决 merge 冲突」时，Agent 可以：

1. 列出冲突文件与冲突摘要（可读取冲突标记**仅供说明**，修改前需用户确认方案）
2. 在用户**确认保留策略后**再编辑文件
3. 由用户或 Agent 在用户再次确认后执行 `git add` / `git commit` / `git push`
4. 完成后 `git checkout <DEV_BRANCH>` 切回开发分支

**该模式不得与 `/merge-to-target` 混在一次执行里默认开启。**
